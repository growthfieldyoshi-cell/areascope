## 1. 現行DB調査結果 (実DB実測 / SELECT)

### 1.1 `municipalities` の政令市格納粒度
- 横浜市・川崎市・相模原市は **市単位でのみ存在**:
  - `横浜市` = code `141003` / jis `14100`
  - `川崎市` = code `141305` / jis `14130`
  - `相模原市` = code `141500` / jis `14150`
- **行政区(`〇〇市〇〇区`)の行は全国で0件**。`municipalities` は政令指定都市の行政区を保持していない。
- 一方 **東京23区(特別区)は23行すべて存在**。特別区は独立した地方公共団体のため通常市と同じ扱い → **特別区は本課題の対象外**(既に投入可能)。
- → 課題は「政令指定都市の**行政区**」に限定される。

### 1.2 `stations` の政令市区粒度
- 横浜市内の駅は `municipality_code`(5桁生コード)に **区単位コード 14101〜14118 の18種**を保持。
- ただし `municipality_code_normalized`(6桁)は **全駅 `141003` に集約**、`municipality_name` は「横浜市」1種、`municipality_slug` は `yokohamashi` の1種。
- → stations は「区コードは持つが、ページ用キーは市単位に正規化」する設計。市区町村ページも **横浜市で1ページ**(区ページは存在しない)。

### 1.3 `municipality_populations` の粒度
- `141xx` 系コードに **市コード `14100` と区コード `14101〜14118` の両方が存在**。
- → 人口データは区粒度・市粒度の両方を持っている(不動産データとは別系統)。

### 1.4 XIT001 API の政令市区取得可否(実測 / 各1リクエスト)
| リクエスト | 結果 |
|---|---|
| `city=14103`(横浜市西区) | **HTTP 200 / 216件** / Municipality="横浜市西区" → **区単位で取得可能** |
| `city=14100`(横浜市の市コード) | **HTTP 404** → **市単位の一括取得は不可** |

- **XIT001 は行政区粒度でしか取得できない**。政令市全体のデータを得るには **各区を個別に取得して合算**するしかない(横浜18区・川崎7区・相模原3区)。

## 2. 政令市区の課題

1. **データ取得は区単位必須** — XIT001 は市コードを受け付けない。横浜市全体には18区ぶんのリクエストが要る。
2. **投入先キーが無い** — `real_estate_transactions_raw.municipality_code_6` / `real_estate_market_stats(_annual).municipality_code_6` はいずれも `municipalities(code)` への FK。区の6桁コードは `municipalities` に無いため、区コードでは **FK制約違反でINSERT不可**。
3. **ページは市単位** — 既存の市区町村ページ・stations・slug はすべて政令市を市単位(横浜市1ページ)で扱う。区ページは存在しない。
4. **全国波及** — 同じ構造の政令指定都市が全国に20市(札幌・仙台・さいたま・千葉・川崎・横浜・相模原・新潟・静岡・浜松・名古屋・京都・大阪・堺・神戸・岡山・広島・北九州・福岡・熊本)。東京23区は特別区のため対象外。

## 3. 設計案比較

### 案A: `municipalities` に行政区レコードを追加する

区(例: 横浜市西区 jis `14103` / 6桁 `141038`)を `municipalities` に追加し、不動産テーブルの FK をそのまま使う。

| 観点 | 内容 |
|---|---|
| メリット | データモデル上もっとも正統。区を独立エンティティとして扱え、将来「区ページ」も作れる。不動産テーブルの FK・CHECK をそのまま使える |
| デメリット | アプリ全体が参照する**マスタテーブルへの大量追加**(政令市20市で約175区)。6桁コードの検査数字を正しく採番する必要。`municipalities` を全件走査する既存処理(一覧・件数・ランキング等)の挙動が変わるリスク |
| 既存ページへの影響 | **大**。`/city` 一覧、市区町村数カウント、人口ランキング等が区を市と同列に数え始める可能性。回避には `is_public` 等のフラグ追加=さらにマスタ改修 |
| stations/population/sitemap/canonical | stations は `municipality_code_normalized=141003` のままで不整合化(駅は市、不動産は区)。sitemap に区ページを足すか否かの判断も発生。canonical 設計の見直し要 |
| 実装難易度 | 高(マスタ採番 + 既存処理の影響調査 + フラグ設計) |
| 全国展開への適性 | 区マスタさえ整えばスケールはする。ただし初期コストが重い |

### 案B: 不動産データだけ区単位で別管理する

区マスタ(`real_estate_wards` 等)を不動産連携内に新設し、不動産テーブルは `municipalities` ではなくその区マスタを参照(または親市コードを併記)。

| 観点 | 内容 |
|---|---|
| メリット | `municipalities` を触らずに区粒度を保持できる。不動産機能内に閉じる。将来 区ページ化も可能 |
| デメリット | 自治体マスタが2系統に分裂(`municipalities` と区マスタ)。区→親市の対応表を自前管理。集計・JOIN が複雑化。FK 設計のやり直し |
| 既存ページへの影響 | 小〜中。既存ページは `municipalities` のままなので直接影響は少ないが、市区町村ページで政令市の不動産を出すには「市ページ←区マスタ集計」のJOIN経路を別途用意 |
| stations/population/sitemap/canonical | stations/population/sitemap は変更不要。canonical も既存維持。ただし区マスタと stations の区コードを別管理する重複が発生 |
| 実装難易度 | 中〜高(新マスタ + 対応表 + 不動産テーブルの FK 再設計) |
| 全国展開への適性 | 良い。区粒度を保ったまま全国の政令市に拡張できる。区ページ化の余地も残る |

### 案C: 政令市は市単位に集約して表示する

XIT001 で全区を取得 → raw の `municipality_code_6` には**親市コード(横浜市=`141003`)を入れて投入** → 集計も市単位。区の識別は `raw_payload` / `district_name` / `district_code` に保持。

| 観点 | 内容 |
|---|---|
| メリット | **`municipalities` も DDL も変更不要**。既存 FK・CHECK・既存テーブルがそのまま使える。既存サイト構造(政令市=1ページ)と完全に一致。市区町村ページの annual優先表示ロジックもそのまま動く |
| デメリット | 区粒度が集計テーブルから失われる(raw には district 情報が残るので再集計は可能)。「横浜市西区ページ」は作れない。取得運用は区単位ループ(横浜18区)が必要 |
| 既存ページへの影響 | **ほぼ無し**。横浜市ページに市全体の不動産統計が出るだけ。stations が既に市単位に正規化済みなので JOIN もそのまま(`stations.municipality_code_normalized=141003` ↔ `market_stats.municipality_code_6=141003`) |
| stations/population/sitemap/canonical | **すべて変更不要**。stations の正規化方針と一致、sitemap/canonical も既存の市ページのまま |
| 実装難易度 | 低〜中(取得スクリプトに「区コードリスト→親市コードへ集約」ロジックを足すだけ。raw投入のバッチ置換単位は `親市コード × year × quarter × price_category`) |
| 全国展開への適性 | 良い。政令市ごとに「区jisコード一覧→親市6桁コード」のマップを持てば全国20市に同じ方式で展開可能 |

### 案D: 当面は政令市区を対象外にする(現状維持)

| 観点 | 内容 |
|---|---|
| メリット | 追加作業ゼロ。通常市の拡張に集中できる |
| デメリット | 横浜・川崎・相模原という人口最大級エリアの不動産データが永続的に欠落。全国展開時に政令市20市すべてが穴になる |
| 既存ページへの影響 | 無し(現状どおり政令市ページは不動産セクション非表示) |
| stations/population/sitemap/canonical | 影響なし |
| 実装難易度 | なし |
| 全国展開への適性 | 低い。主要都市が抜けたカバレッジになる |

## 4. 推奨案

**案C(政令市は市単位に集約して表示)を推奨。** 必要なら将来 案B へ発展。

理由:
- AreaScope は **既に政令市を市単位で1ページ運用**しており(stations が `municipality_code_normalized` で市集約、横浜市ページは1枚)、案Cはこのサイト構造と完全に整合する。
- **`municipalities` にも DDL にも一切触れない** — 既存マスタ・既存ページ・stations/population/sitemap/canonical への影響が無く、最小リスク。
- raw に `district_name` / `district_code` / `raw_payload` を保持済みのため、**区粒度の情報は失われず**、将来「区ページ」が必要になった時点で raw から区別に再集計できる(案B/案Aへの移行余地が残る)。
- 全国展開も「政令市ごとの区jisコード一覧」を定数で持てば同方式でスケールする。

懸念と対応:
- **取得運用**: 政令市は区数ぶんのリクエストになる(横浜18・川崎7・相模原3 = 28リクエスト)。`year×quarter` 込みで横浜だけ72リクエスト。レート・実行時間に注意。
- **バッチ置換単位**: raw の置換キーは「親市コード × year × quarter × price_category」。1政令市の全区を取得し終えてから DELETE→INSERT する(区ごとに置換すると後続区の取り込みで親市分を消してしまう)。または「親市×year×quarter×price_category」を1回 DELETE し、全区ぶんをまとめて INSERT する運用にする。
- **annual 集計**: 既存ロジックどおり raw を `municipality_code_6(=親市)` で集計すれば、市単位の通年集計がそのまま出る。
